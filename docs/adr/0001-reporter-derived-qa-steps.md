# Derive QA Steps from existing tests with a reporter, not a fixture

qa-instructions previously required tests to be rewritten around a `qa` fixture (`qa.step(action, expected, fn)`), with steps authored by hand and `test`/`expect` re-exported from the package. That defeated the point: existing tests produced nothing until rewritten, and importing Playwright at runtime from the package broke it when installed by link (two Playwright instances). We now derive QA Steps automatically from what each test already does, using only a Playwright reporter plus a trace setting in the project's config. Tests are not changed, Playwright is a peer dependency only, and the package never loads Playwright at runtime.

Steps come from the reporter's `pw:api` steps (browser actions a person can repeat; plumbing like waits and value reads is dropped), Expected Results from the `expect` steps that follow each action, and Sections from the test's own `test.step` blocks (configurable). Step Screenshots come from the trace: on Playwright 1.63+, `trace: { mode: 'on', snapshots: { screen: true } }` records a screenshot per action, joined to the reporter step through the trace's step and call IDs. Older Playwright is supported with rougher output (title parsing and nearest screencast frame). The trace file layout is not a documented Playwright API and already differs between releases (1.63 writes version 9; Playwright `main` writes version 10, which drops the separate step-id mapping), so all trace reading lives behind one screenshot-source port whose adapter handles each supported trace version and degrades to instructions without screenshots on an unknown one. We checked `@andrii_kremlovskyi/playwright-traces-reader` (4.2.5) against a real 1.63 trace and read the trace ourselves instead (see "Trace reader" below). Prior-art research found no existing tool that does this without test changes (see `docs/research/2026-09-26-auto-derived-qa-steps-prior-art.md`).

## Hexagonal core, runner adapters at the edge

All logic (turning actions and checks into QA Steps, Sections, Expected Results, choosing screenshots, masking secrets, rendering) lives in a runner-independent core with ports: an inbound port that accepts a neutral stream of test events (action, check, group start/end, screenshot reference), and outbound ports for screenshot sources and output writers. No core code depends on Playwright's `Reporter`/`TestStep` types or on Jest's. The Playwright reporter is a thin adapter that translates reporter events (and trace screenshots) into core events; a Jest adapter can later feed the same port without touching core logic.

## Script changes and forced Actions

A script can change the page (opening every collapsed accordion with `evaluateAll`), leaving a tester stuck. Reporter step data does not say what a script did: `Evaluate` steps carry only the locator, never the expression or its result, and `force: true` is not in any step's params. The trace does, when it has DOM snapshots, and the test's source is the fallback. The core's `ScriptChangeRule` decides from neutral facts on the Action and its capture; only scripts (`evaluate`-family calls) and events fired by script (`dispatchEvent`) can warn, and one that failed never does (the test stops there).

**With a trace.** Playwright takes a DOM snapshot before and after every `evaluate`, `evaluateAll`, `page.evaluate`, and `dispatchEvent` call: 1.53–1.62 name them `before@<callId>` and `after@<callId>`, 1.63 gives the call id and a `phase` instead. `locator.evaluate()` is traced only as the `waitForSelector` that finds its element; the script then runs untraced, so its effect is read from the page's next snapshot (the next call's `before`). The adapter compares the two snapshots' DOM, form values, and scroll offsets (ignoring the target marker) and reports `pageChanged` on the capture. The trace also records every call's full options, so `force: true` is seen however the test built them (`click(opts)`), reported as `forced`.

- **Changed or not.** A script whose snapshots differ is a warning step at that point, carrying the checks that follow it as its Expected Result so the tester sees what to restore by hand, whatever the test did with its result. One whose snapshots match is dropped, and its checks join the step before it; in the `collapse` presentation a group it no longer interrupts stays one QA Step. So the befstore test that opens every `details:not([open])` warns only on product pages that have a collapsed section, and `scrollTo(0, 0)` on a page already at the top does not warn.
- **What changed.** When the only difference between the two snapshots is which `<details>` sections are open, the adapter reports those sections on the capture (`sectionChanges`), each named by its `<summary>` text. The core then words the warning in page terms: "The test opened the **Shipping** and **Returns** sections with a script instead of a user action. Click each one to open it if it is closed." (or closed, for sections it closed). Any other change, a section without a heading, a script that both opened and closed sections, or no DOM snapshots keeps the plain warning, which names the element only by what a tester sees. `dispatchEvent('click')` warnings already name the element to click.
- **Forced.** The call's recorded `force: true` marks the Action approximate.

**Without a trace, or without DOM snapshots** (e.g. 1.63 with `snapshots: { dom: false }`), the adapter reads the test's own source at the step's `location` (a lexical reading, not a parser):

- **Changed or read.** An event fired by script always changes the page. An `evaluate`-family call whose result the test uses (assigned, awaited inside an expression, returned, passed on) read the page: no warning. One whose result is discarded (`await locator.evaluateAll(...)` as its own statement), or whose call site cannot be read, may have changed the page: a warning step.
- **Forced.** `force: true` written in the call's options (or a `force` param, should a runner report one) marks the Action approximate.

Limits: without a trace, a discarded script that changed nothing still warns, a script whose result is used but that also changed the page does not, and options built elsewhere are not seen as forced. With a trace, the page changing by itself while the script runs (a timer, a late response) counts as the script's change, and a `locator.evaluate()` that is the test's last call falls back to the source reading, since no later snapshot exists. The warning cannot say what to do ("open it"), only that the page changed and what the test checked next.

## Trace reader

The screenshot adapter reads `trace.zip` itself, unzipping with `fflate`. `playwright-traces-reader` does not fit. Against a real 1.63 trace it only surfaces `screencast-frame` images and never the per-action `screenshot` events that `snapshots.screen` writes (`screenshots/<callId>-{before,action,after}.png`). It also ignores the `input` events that carry the element box and click point. It extracts every trace into a temporary cache directory on disk, and it brings in a CLI dependency (`commander`). The format knowledge we need is small: context-options `version`, `before`, `input`, and `screenshot` events.

The join is: reporter `pw:api` step → the test runner's `test.trace` `before` event → the library call → its screenshots and input. Reporter steps have no id, so a step is matched by its position among the test's `pw:api` steps plus its title. Steps with a `group` (getters, configuration fixtures) are traced but never reported, so they are not counted. In version 9, library `before` events link to the step through `stepId`. In version 10 (verified with `1.64.0-alpha-2026-09-26`), the step id is itself the library `callId`, and screenshot files are named after it. The committed sample traces in `packages/playwright/test/fixtures/traces/` cover both. Any other version gives no screenshots.

Playwright 1.53–1.62 write version 8, linked like version 9 but with no per-action screenshots; 1.53–1.54 also write every test-runner step's `method` as `step`, so a `pw:api` step is known by its call id. Without per-action screenshots (version 8, or a later trace without `snapshots.screen`), a call's Step Screenshot is a `screencast-frame` of the call's page; frames are `resources/<sha1>` in version 8 and `screencast/<name>` from version 9. Version 8 `input` events carry the click point but no element box, and no time: the Action is dated by the DOM snapshot its `inputSnapshot` names (`input@<callId>`), on the recording's clock.

What the recording shows, and when (QI-30, measured on 1.56 against a long fixture page and the befstore trial). A `screencast-frame`'s `timestamp` is when Playwright received it; its `frameSwapWallTime` (present 1.53–1.62) is when the browser painted it, on the wall clock, which the context options' `wallTime`/`monotonicTime` pair converts (receipt trails paint by 1–4ms). The recording is not a clock-driven video: Chromium sends a frame only when the page repaints and the last frame has been acknowledged, and Playwright holds acknowledgments (in 1.53–1.58 on 35ms ticks, 200ms once throttled; 1.60 throttles to 200ms outside a 500ms window after each call), releasing them at each call's `before`, input, and `after`. A pointer Action logs `scrolling into view if needed`, scrolls, then takes the input snapshot and sends the input 1–2ms later; a fill takes its input snapshot first and scrolls as it focuses the field. The DOM snapshots record every element's scroll offsets (`__playwright_scroll_top_`), and write only what changed since the frame's previous snapshot (`[[snapshotsAgo, nodeIndex]]` references otherwise), so the page's scroll position and DOM at each `before`/input/`after` moment are known. The findings: (1) a frame painted shortly after a change can still show the page before it: a frame painted 0.2ms after a click's scroll, 0.7ms before its input, showed the old scroll position (the befstore click dot on the heading), and across 40 runs frames painted up to 15ms after a recorded scroll showed the old one; (2) when a click scrolls, no frame is painted between the scroll and the input late enough to show it; (3) the recording can go quiet while the screen is out of date: after a fill that scrolled, the only frame painted in the next 340ms showed the page top, because the repaint that showed the scroll came while its predecessor was unacknowledged and nothing repainted after; so an old last frame does not mean an unchanged page; (4) the frame last painted by a call's `after` often predates the call's effect (the befstore "Type 3" screenshot), while one painted after it and before the next Action's scroll shows it; (5) on a page that scrolls smoothly (`scroll-behavior: smooth`, the befstore store pages; QI-33), a fill's focus starts a scroll that runs for hundreds of milliseconds after the fill ends, while its `after` snapshot and the next call's `before` still record the old scroll offsets: frames painted in the first 50–400ms after the fill show the page still near the top, and the last frame before the next Action (a click waiting for its button to stop moving) shows the page settled, the field at the bottom edge. A `check` of a box already as asked sends no input and never scrolls to it (no `input` event), so no frame of it is known to show the box.

So, with PAINT_LAG = 50ms (the longest observed stale lag was 15ms): a call with a point or box, whose input time is known, gets the last frame painted at or before the input (a later one may already show the click's effect), with moment `action` (highlighted; with no box, by the click dot alone), only when that frame was painted at least PAINT_LAG after the page's DOM snapshots last recorded a change before the input (the element Playwright marks as a call's target aside), or, for a frame no more than 50ms old, at least PAINT_LAG after they last recorded a change in scroll offsets. A click Playwright scrolled to is therefore never marked, and no dot is drawn on a frame whose scroll position may differ from the input moment's. Otherwise the Step Screenshot has moment `after` (no Highlight) and is a frame painted after the call ended and before the next call on the page may have changed it (calls that only read or wait do not; one that acts on an element does from its scroll log or input, any other from its start): the last one painted in that window, since the recording gets a frame only when the page repaints, so the last frame shows the page as the Action's effect settled, where an earlier one may catch a smooth scroll still under way. Without one, the last frame painted by the end, else the page's first frame; except that an Action that sent input to an element without a point (a fill, which records an `input` event with its input snapshot) and changed the page gets no screenshot, since every frame by its end may predate its scroll and its value. A fill has no point or box before 1.63 and gets this frame, which shows what was typed when the recording has it. A `check` or `uncheck` that sent no input (the box was already as asked) gets no screenshot on any version, since Playwright never scrolled to the box; on 1.63 its before and after screenshots would show wherever the page happened to be. Playwright 1.63+ per-action screenshots are otherwise unchanged; on 1.63 a fill whose field is below the fold is photographed, and outlined, before its focus scrolls the page, and on a smoothly scrolling page its `after` screenshot, taken within 20ms, still shows the page top (a separate issue: no per-action screenshot shows the settled scroll).

## Masking secrets

Whether an Action typed into a password field is read from the page as the trace recorded it, not from the test code (a locator like `getByLabel('PIN')` says nothing about the field's type). With `snapshots: { dom: true }`, every library call's `frame-snapshot` events (keyed by `callId` and phase) serialize the DOM with the element the call touched marked by a `__playwright_target__` attribute, alongside its own attributes such as `type`. The trace adapter reports, per Action, whether that element is an `input` of type `password` as a neutral `passwordField` fact on the Action's capture; without DOM snapshots the fact is unknown and only configured patterns apply. Nothing fails either way.

Masking itself is core logic. The recorder phrases a password Action as "Type your password into …", then masks every piece of text in the bundle (step text, Expected Results, URLs, Section and test titles) against the typed password values plus the reporter's `mask` strings and regular expressions, before the bundle is written. Every renderer reads that bundle, so every output format is masked. Playwright's own step titles and params carry typed values (`Fill "…"`), but they never reach the bundle: the adapter's Action refs contain the title only in memory. Screenshots are not masked: password inputs already render as dots, but other masked values can still show in a Step Screenshot.

## Naming elements

A tester cannot see a test id or a CSS selector, so a QA Step never shows one. Elements a test found by role, label, text, placeholder, alt text, or title keep the name the test gave them. For the rest, the trace adapter reads, per Action and per check, the element the call touched from its first DOM snapshot that marks it, and reports neutral facts on the capture (`RecordedElement`): tag, attributes, the text a person can see inside it (skipping hidden, `aria-hidden`, script, and style content), and the text of what labels it (`aria-labelledby`, `<label for>`, or a `<label>` around it). The core's `ElementNamer` decides the words: the element's role (explicit, or implied by its tag and `type`), then its name in the order browsers name elements (labels, `aria-label`, a button input's value, alt text, visible text for roles named by their content, `title`, a field's placeholder). A field is named by its label alone ("Type **3** into **Quantity**"), anything else as "the **Add to Cart** button". A check about an element's text does not name the element by that text; an unnamed one becomes "the page". Without DOM snapshots, the adapter reads what a CSS selector requires of its element (tag and `type`, from the last compound of the first selector in a list, parsed with `css-what`), and the step says only that: "the button", "the number field", or "the element".

A check's element comes on its `CheckCapture` (see "Older Playwright step data"); the library's `expect` call marks its element in its `after` snapshot. A check whose subject the runner could not name is an element check when the page recorded one. On an element with no name from the test, a name from the page beats the author's description (`expect(el, 'purchase form')`), and the description beats a bare kind ("the element").

Several parts of a page can hold elements that read the same (one product form per product, each with its quantity field and Add to Cart button). The adapter reports two more facts on `RecordedElement`: `lookalikes`, how many elements in the snapshot have the same tag, `type`, role, and visible words (text, labels, `aria-label`, alt, title, placeholder, a button input's value); and `region`, the part of the page the element sits in. The region is the element the test narrowed its search to, when the call's selector has an outer part in plain CSS (`#edd_purchase_102 >> input[…]`, matched against the element's ancestors with `css-select`) and that element has a title; otherwise, only when there are lookalikes, the largest titled ancestor holding none of them. `<html>` and `<body>` never count. A title is the part's `aria-labelledby` or `aria-label`, else the first visible heading, legend, or caption inside it that does not hold the element, else a heading just before it. The core's `RegionNamer` decides whether to use it: only when the region is the test's own scope or the element has lookalikes, and only when it has a title ("… in the **Renewable Energy Certificates (RECs)** form"; a form, dialog, row, table, or navigation by its role, any other part a section). Actions and checks share the wording.

A snapshot refers back to unchanged subtrees of earlier snapshots of the same frame (`[[snapshotsBack, nodeIndex]]`, counting that snapshot's nodes in post-order), so the adapter keeps every snapshot per frame and resolves references into a `domhandler` document to read labels and text. Only an element a snapshot writes out itself can be its call's target: before 1.63 the mark is the call id and stays on an element after its call, so a mark reached through a reference, or naming another call, is stale.

## Highlights

The core decides what a Highlight marks and where (`HighlightPlanner`); a screenshot-annotator port paints it, and the default adapter composites an SVG overlay with sharp. sharp is a dependency of the Playwright package, never the core. Decisions:

- **Scale from the image, not the device.** The element box and click point are viewport CSS pixels. The planner scales them by the image's size over the viewport's (read from the trace's context options), so it stays right whatever pixel density the screenshot has. Playwright 1.63 writes `snapshots.screen` images at CSS scale even with `deviceScaleFactor: 2`, so the scale is 1 there today.
- **Drawn after the run, replacing the original.** Highlighting happens as each bundle is written; the highlighted image replaces the original, and the bundle's asset records its marks. Keeping both would double every bundle for a view only `highlight: 'none'` needs.
- **Only on screenshots that match the box.** The box is read at the moment of the Action. Action-moment and before-moment screenshots are highlighted; after-moment ones are not, since the page may have navigated or closed a menu.
- **Warning steps get none; approximate steps get a dashed outline.** A forced Action's element may have moved while it was clicked, so the outline is drawn where the element was, dashed to say so, and the step's text says the highlight may not line up.

## Older Playwright step data

Before 1.63, reporter steps have no `subtitle` or `params`. The title carries them instead (`Fill "demo-user" getByLabel('Username')`, `Navigate to "/"`), so a step without `params` is read from its title. A check's title names only the matcher (1.57–1.62 add its locator), so its subject and expected value are read from the test's source at the check, like the script and force facts above: `expect(<subject>)[.not].<matcher>(<literal>)`. An expected value written as a literal, or as a constant declared once in the file with a literal, is read; other expressions, and checks whose subject is a variable, are not resolved.

A check given a message (`expect(qty, 'cart line-item quantity').toBe(3)`) is titled with the message on every version, and no step field names its matcher, so the matcher and `.not` are read from the source at the check, and the message becomes the check's neutral `description`. The core words a plain value's check only when it has a description and a known expected value ("**cart line-item quantity** is **3**"); on an element, the description replaces a name a tester could not use (a CSS selector, a role without a name, or a variable the source reading cannot resolve), since a matcher only locators have (`toBeVisible`) tells the adapter the subject is an element.

With a trace, what the source cannot say is read from it. The test runner's trace previews each `expect` step's expected value (`params.expected`), even one the test computed (`toBeCloseTo(QTY * UNIT_PRICE)` → `15`); an object, such as a regex, previews as `Object` and is ignored. A check the browser ran (`Frame.expect` in the library trace, linked to the step like an Action's call) records the element's selector (`#purchase_1174 >> input[name="…"] >> nth=0`, read into the same ElementTarget the equivalent locator gives) and its expected text or pattern (`expectedText: [{ regexSource: 'login-error' }]`). Checks are joined to their trace entries the way Actions are: by position among the test's `expect` steps plus title. The trace reaches the core through the screenshot-source port as a `CheckCapture` per check `ref`, so checks are phrased when the bundle is recorded, not as they arrive; the core fills in only what the reporter step did not say, so 1.63 output changes only where its params carry nothing readable: a regex, which reporter params show as `{}`. A plain-text pattern reads as what must appear ("contains **login-error**"); any other is shown as written. Without a trace, checks are read from the source alone, as above.

1.52 and earlier title steps by API name (`locator.click`) and write trace version 7; they are not supported, so the peer dependency floor is 1.53. The adapter tests run recorded 1.56 and 1.63 reporter steps (`test/fixtures/steps/`) and 1.56 sample traces (`v8.zip`, `v8-scroll.zip` of a long page Playwright scrolls on, and `v8-smooth.zip` of a smoothly scrolling one with an already checked radio, a fill, and a click at once after it); `examples/derived-steps-1.56` runs the derived-steps tests pinned to 1.56 against the 1.63 goldens, including a fill and a click far below the fold, on an instantly and a smoothly scrolling page, whose screenshots are probed.

## Setup mistakes

A missing trace (no `trace` attachment), an unsupported trace version, or an unreadable trace gives text-only QA Instructions and one warning per run on stderr; the missing-trace warning names the config line for the project's Playwright version (`FullConfig.version`). Every reporter hook catches its own errors and logs the first one, so the reporter never fails the test run.

## Considered Options

- **Keep the fixture**: rejected; requires rewriting tests and bundling Playwright.
- **Monkey-patch `page` methods**: rejected; alters Playwright behavior.
- **Screenshot only at end of test (`screenshot: 'on'`)**: rejected; one image per test, not per step.
