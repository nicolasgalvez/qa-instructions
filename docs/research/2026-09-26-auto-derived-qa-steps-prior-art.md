# Prior art: QA steps derived automatically from unmodified tests

Research date: 2026-09-26. Sources: official docs, npm registry metadata (`npm view`), GitHub READMEs, and source code read through the GitHub API. Where a claim rests on a README rather than source, the notes say so.

## 1. Question

Does any existing tool generate **human-repeatable manual QA instructions** (numbered steps a non-technical tester can follow, each with an Expected Result and one screenshot) **automatically from existing, unmodified Playwright tests**? It must derive steps from the actions the test performs (clicks, fills, navigations) and Expected Results from its assertions, without a custom fixture, wrapper, or test rewrite. The same question applies to Jest with Puppeteer or the Playwright library.

This replaces the question behind [2026-03-27-competitive-and-api-research.md](./2026-03-27-competitive-and-api-research.md), which compared tools against the old fixture design (`qa.step(action, expected, fn)`). The design under test now is [ADR 0001](../adr/0001-reporter-derived-qa-steps.md): a Playwright reporter plus a trace screenshot adapter, feeding a runner-agnostic core.

**Pass criteria (all required):**

- **A. No test changes.** Configuration in `playwright.config.ts` is allowed. Imports, fixtures, wrappers, `test.step`, IDs in titles, and attach calls are not.
- **B. Steps derived automatically** from actions (`pw:api`), with Expected Results derived from assertions (`expect`).
- **C. One screenshot per step.**
- **D. Output a tester can follow**, not a developer report.

## 2. Verdict

**Build.** No surveyed tool passes all four criteria, and none fails only on a small, contributable gap.

- **Nothing to reuse whole.** Tools that need no test changes (Playwright's HTML report and trace viewer, allure-playwright, monocart-reporter, testomat.io, Currents, playwright-xray) produce developer reports or TMS status syncs, and none produces a screenshot per action. Tools that produce human-facing step documents (playwright-scenario-recorder, playwright-checkpoint, docs-tests, Serenity/JS) all require explicit authoring in the test by design.
- **No upstream target.** Adding automatic `pw:api` derivation to docs-tests, playwright-checkpoint, or scenario-recorder would reverse each project's core premise (hand-written prose at chosen capture points). That is not a focused PR.
- **Closest prior art: [GemTalk/Jasper `storyboard.ts`](https://github.com/GemTalk/Jasper/blob/main/acceptance/reporters/storyboard.ts).** It is an in-repo reporter, not a package. It phrases `pw:api` and `expect` step titles into sentences ("Click the Save button", "The Rowan row is visible"), but its screenshots come from images the test harness attaches, and it assumes playwright-bdd Gherkin steps. It shows the step-derivation approach works. It does not solve screenshots or packaging. MIT, so its phrasing tables are a legitimate reference.
- **Worth evaluating for one component:** [`@andrii_kremlovskyi/playwright-traces-reader`](https://github.com/Kremliovskyi/playwright-traces-reader) could serve as the trace-reading module behind the screenshot adapter. It is covered in section 5 with its caveats.
- **Commercial near-miss:** Allure TestOps (paid) can "Convert into manual" an automated test case and copy its scenario from the test result's steps. It works one case at a time, detaches automation, and carries no per-step screenshots (section 4).

**Jest:** nothing found. Neither Jest nor jest-circus records browser actions as steps, and allure-jest creates steps only through explicit `allure.step()` calls (section 6).

## 4. Notes

**Serenity/JS.** The handbook's pitch that you can "keep using Playwright Test… start with reporting" is true for scenario-level results only. In source, `SerenityReporterForPlaywrightTest` has `onStepBegin` and `onStepEnd` commented out. `PlaywrightStepReporter` only forwards Screenplay `Photo` artifacts and tags. The Photographer docs say it listens to `InteractionStarts` and `InteractionFinished`, which only Screenplay interactions emit. Getting steps and screenshots means rewriting tests as Screenplay tasks.

**allure-playwright.** This is the strongest "no test changes" candidate for step derivation. `detail` defaults to `true`, and `#shouldIgnoreStep` keeps `pw:api`, `expect`, and hooks, dropping only `route.continue()`. It does not pair checks with actions, filter plumbing (waits, evaluates), or phrase titles for humans. Screenshots attach only at test level (Playwright's `screenshot` option, which fires "after each test"). The trace is attached as a blob for the trace viewer, not split into frames.

**Allure TestOps "Convert into manual".** The docs say you can "convert the test steps from test results to a test scenario", then "Detach automation". So a per-case, manual, one-way conversion exists in a paid product. It works on raw step titles. The docs do not mention screenshots or Expected Results in the converted scenario, which is unverified. It also severs the link to future runs, which defeats regeneration on every run.

**TMS reporters (Qase, TestRail, Zephyr, Xray, testomat.io, TestPlanIt).** Each one is built to sync status against cases a human already wrote. They need case IDs or `test.step` in the test, and none turns `pw:api` into case steps. Xray's README states that steps must already exist in the Jira test issue.

**Jasper storyboard.** This is the only code found that does criterion B the way ADR 0001 describes: walk `result.steps`, keep `pw:api` and `expect`, phrase `getByRole(...)` locators as "the _Name_ _role_", map matchers (`toBeVisible` → "is visible"), and drop CSS-only locators rather than print a selector. Its screenshots are attached by the acceptance harness, and it only reads inside Gherkin `test.step`s, so it fails A and C for arbitrary suites. It is not published. It is useful as a reference for the phrasing tables, not as a dependency.

**Playwright's own pieces.** Playwright supplies everything needed, but no product assembles it. `trace: { mode, snapshots: { screen: true } }` ("Capture a screenshot of the page on every action", 1.63) supplies criterion C. Reporter `pw:api` and `expect` steps supply B. There is no built-in Markdown or instructions reporter.

## 5. Findings that affect ADR 0001

- **The trace schema changes after 1.63.** Playwright 1.63.0 ships trace schema **9** (`latestVersion: trace.VERSION = 9` in [`traceModernizer.ts@v1.63.0`](https://github.com/microsoft/playwright/blob/v1.63.0/packages/isomorphic/trace/traceModernizer.ts)). `main` is at **10** and keeps a `_legacyCallIdToStepId` map ([`traceModernizer.ts@main`](https://github.com/microsoft/playwright/blob/main/packages/isomorphic/trace/traceModernizer.ts)). traces-reader's compatibility notes say schema 10 "unifies library and test runner action IDs in `callId` and removes the separate `stepId` mapping" (validated against `1.64.0-alpha-2026-09-14`). The ADR's join "through the trace's step and call IDs" therefore has to handle both shapes: a v9 step-to-call mapping, and v10 where the reporter step ID is itself the `callId`. The ADR already puts the version check in one module, and this is the first concrete case for it.
- **Possible reuse for the trace module.** `playwright-traces-reader` already handles schemas up to 10, both resource-reference layouts, and action-to-screenshot pairing (`digest`). It has two dependencies (`adm-zip`, `commander`) and no Playwright runtime dependency, which fits the ADR's rule that the package never loads Playwright. Risks: one maintainer, 3 stars, and a v4 major after six months, which suggests API churn. Its compatibility guarantee covers traces inside a Playwright **HTML report**, while raw library traces are "not yet part of the compatibility guarantee". Its `digest` pairs actions with the _nearest screencast_ screenshot, which may not match the 1.63 per-action `screen` snapshot. Whether it reads the `screen: true` snapshots specifically is **unverified**. Check that against a real 1.63 trace before adopting it. Otherwise, keep the ADR's own module and use this library's source as a reference for the schema differences.

## 6. Jest (+ Puppeteer / Playwright library)

- **No equivalent tool found.** Jest's reporter and `TestEnvironment` APIs expose test-case and hook events, not browser actions ([previous research §5](./2026-03-27-competitive-and-api-research.md#5-jest-reporter--testenvironment-api)). allure-jest creates steps only through `allure.step()` and `allure.logStep()` ([Allure Jest docs](https://allurereport.org/docs/jest/)). jest-puppeteer, expect-puppeteer, jest-html-reporter, jest-junit, and jest-ctrf-json-reporter have no step or action capture (npm search above).
- **Implication for the design, not a finding about a tool:** under Jest, the only automatic source of actions is the browser library itself. With the Playwright library, `context.tracing` records every action and (1.63+) a screenshot per action, so a Jest adapter could feed the core from the trace alone. Jest's `expect` calls are not in that trace, so Expected Results would be missing unless the tests use Playwright's `expect`. This is **unverified**: nothing surveyed does it, and traces-reader explicitly does not guarantee raw library traces. Puppeteer has no comparable action trace.
